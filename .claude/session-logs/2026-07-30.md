### Timezone Bug

User reported a print saved "last night" showing today's date. Root cause: `TIME_ZONE = 'UTC'` in `config/settings.py` — with `USE_TZ=True`, Django uses `TIME_ZONE` both to render all `printed_at` display and to interpret naive datetimes (e.g. the manual-entry flatpickr's local wall-clock string). Late-night Eastern saves landed after midnight UTC and rendered as the next day everywhere (print history, dashboard, and the daily-usage chart's "today" boundary). Changed to `America/New_York` (inferred from the FPL electricity-rate default already in the calculator — flagged to the user as an inference, not confirmed). Verified against real data: a print stored as `2026-07-30 00:07 UTC` now correctly displays as `Jul 29` (its actual Eastern local time) everywhere.

**Files changed:** `config/settings.py`

### Dark Mode

User asked for a persistent dark mode, with spool colors staying their own actual color regardless of theme.

- Toggle (sun/moon icon in the nav) flips a `theme` key in the Django session — same mechanism the existing Inventory Cards/Grouped toggle already uses, so it persists across navigation and reloads for the length of the login session (resets on logout, since Django flushes session data then; not tied to the user account).
- New `tracker/context_processors.py` (`dark_mode`) injects the flag into every template; `tracker.views.toggle_theme` (POST-only) flips it and redirects back.
- `tailwind.config.js`: `darkMode: 'class'`; `base.html`'s `<html>` gets the `dark` class conditionally.
- Applied `dark:` variants across all 28 templates via a small Python script (mapped ~50 recurring light-mode Tailwind tokens — `bg-white`, `text-gray-*`, `border-gray-*`, etc. — to dark equivalents, idempotent, appended rather than replaced). Two bugs surfaced by a follow-up audit script and fixed before shipping:
  1. The bulk substitution's word-boundary matching also matched inside `hover:`-prefixed classes (e.g. `hover:text-indigo-800` triggering an unprefixed `dark:text-indigo-300`), which would have made a few elements permanently wear their hover color in dark mode instead of only on hover. Audited all 562 injected tokens, found 95 instances of this, removed them (each case had a correct alternative already present, or fell back cleanly to the untouched base color).
  2. ~46 hand-coded `<input>`/`<select>` elements across 13 templates (everything not routed through the shared `forms.py` widget classes) had no explicit background color at all, so the bulk script had nothing to attach a dark variant to — they'd have stayed white boxes. Fixed by giving them the same `bg-white ... dark:bg-gray-900` treatment as the shared form-input class.
- `forms.py`'s shared `_input_cls` (used by every Django-rendered form field) updated directly.
- flatpickr's calendar popup ships a light-only theme by default — added a manual `html.dark .flatpickr-*` override block in `base.html`.
- Chart SVG colors (previously raw hex attributes) converted to Tailwind `fill-*`/`stroke-*` classes so they could carry `dark:` variants; checked indigo-600's contrast against the dark card surface (2.33:1, fails ≥3:1) and switched chart lines/markers to indigo-400 in dark mode (4.92:1) accordingly.
- Verified in a real browser across Dashboard, Inventory (list + Add Spool form), Print History, Queue, Log a Print, Calculator, and Sales Log, in both themes; confirmed spool color swatches are genuinely unaffected (inline `style="background-color"`, never touched by any class-based rule) and toggle state survives hard reloads and cross-page navigation.

**Files added:** `tracker/context_processors.py`
**Files changed:** `tailwind.config.js`, `config/settings.py`, `tracker/{forms,urls,views}.py`, `templates/base.html`, all 26 other templates under `templates/`
