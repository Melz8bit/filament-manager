### Spool assignment: insufficient-filament guard

User's screenshot showed the spool-assignment page defaulting to a spool with 26g
remaining against a 71.2g-needed slot, with no visible warning, and asked for two
things: an at-a-glance cue when a selected spool won't cover the print, and a hard
block on submitting if it would drive a spool negative.

- Traced the existing "continuation spool" feature (amber warning box, JS-driven) —
  it only activates via `onchange` and an auto-check IIFE on page load, both entirely
  client-side. Couldn't confirm from static reading why it wasn't appearing in the
  user's screenshot, but regardless: relying solely on JS for the *initial* page state
  is fragile, so moved the insufficiency computation server-side instead of chasing the
  exact JS bug.
- `_build_slot_dict()` (new shared helper in `views.py`, replacing duplicated
  best-spool-ranking logic in `SpoolAssignmentView.get`, `SpoolSlotRowView.get`, and
  `SplitSpoolSlotView._build_slot`): now also returns `insufficient`, `best_remaining`,
  and `shortfall` for the selected/default spool.
- Template (`spool_slot_row.html`): red "⚠ Not enough remaining" badge next to the
  color-hex label, red ring on the select, and the amber replacement-spool panel
  pre-expanded with the exact numeric shortfall — all rendered server-side so they're
  visible immediately on load, not dependent on JS firing correctly. Existing JS
  (`checkSpoolCapacity`) still handles live re-selection, now also toggling the badge
  and select ring to match.
- **Server-side validation (the actual "don't allow it" gap):** `SpoolAssignmentView.post`
  previously had no rejection path at all — an unresolved shortfall (no continuation
  spool picked, or one that also wasn't enough) still confirmed the print and just
  clamped `spool.remaining_g` to `max(0, ...)`, silently absorbing the deficit. Rewrote
  it to validate every slot's requested deduction up front, before any `.save()` calls;
  if any slot can't be fully covered, the whole submission is rejected with a specific
  per-slot error message and the form re-renders with the user's actual selections
  preserved (not reset to defaults), returning HTTP 400.
- Added a client-side `validateAssignmentForm()` submit guard too (red ring + alert,
  scrolls to the first offending row) as a faster feedback layer — the server check
  above is what actually enforces the constraint.

**Files changed:** `tracker/views.py`, `templates/tracker/partials/spool_slot_row.html`,
`templates/tracker/spool_assignment.html`, `tracker/tests.py`

### Testing

Added `SpoolAssignmentInsufficientFilamentTests` (6 tests) to `tracker/tests.py`:
insufficient default selection flagged on GET, sufficient selection not flagged,
insufficient spool alone rejected (spool untouched, not floored), insufficient
continuation spool rejected, sufficient continuation spool succeeds, exact-match grams
succeeds. First attempt at two of these asserted on raw warning text and failed —

from "hidden" — rewrote to check the pk-scoped `class="hidden ..."` markup directly.
